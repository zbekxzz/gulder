## 1. Контекст

**Flowers** — сервис, который помогает дарителю выбрать букет
и дополнительные подарки для конкретного получателя с учётом повода, бюджета, вкусов,
аллергий, чувствительности к запахам, домашних животных, расположения магазинов, скидок
и **неполноты сведений** (даритель часто не знает, есть ли у человека аллергия или кошка).

Ключевая идея: система **никогда не выдаёт небезопасную рекомендацию** и честно показывает,
насколько она уверена и каких сведений не хватает.

Это личный долгоживущий проект, который будет развиваться и работать на реальных данных, поэтому:
- код пишется так, чтобы в него можно было вернуться через полгода: тесты, понятные имена, ADR на решения;
- любая обратимая миграция, воспроизводимая сборка, работающий CI с первой вехи;
- данные о токсичности растений и аллергенах проверяются по источникам, а не берутся «на глаз»;
- объём делится на два релиза (§6), а не на «успею / не успею».

### Цели (раздел 2 ТЗ)
1. Top-5 букетов с объяснениями и confidence.
2. **Ноль небезопасных рекомендаций** (букеты и подарки) на размеченном тесте.
3. Любая замена состава повторно проверяется на ограничения.
4. AI-ассистент подбирает набор «букет + подарки» в пределах бюджета.
5. Фильтры «Рядом», «Дешевле», «Со скидкой».
6. Необязательный нумерологический режим.
7. Исследовательский режим.

### Вне объёма
Оплата, доставка.

## 5. Основной сценарий (раздел 5 ТЗ)

1. Флорист/магазин загружает каталог букетов и подарков (CSV).
2. Даритель создаёт получателя.
3. Для каждого поля профиля фиксируются **значение, источник и уверенность**: «знаю», «предполагаю», «не знаю».
4. Даритель задаёт повод, бюджет, дату, место, желаемую эмоцию и при желании включает нумерологию.
5. **Rules Engine** исключает известные риски.
6. **Ranker** выдаёт Top-5, **ассистент** формирует наборы «букет + подарки».
7. Даритель применяет фильтры «Рядом», «Дешевле», «Со скидкой».
8. Флорист подтверждает состав или предлагает замену (с повторной проверкой).
9. Фиксируется feedback.

## 6. Функциональные требования

Объём делится на два релиза (раздел 4 ТЗ). **P0** — релиз 1.0: сервис полезен сам по себе и
работает на реальном каталоге. **P1** — релиз 2.0: приглашения получателя, режим сюрприза,
заказ, learning-to-rank. Схема БД и контракт API закладываются сразу под оба, но код P1 не
пишется до закрытия P0; эндпоинты P1 отвечают `501 Not Implemented`.

### 6.1 Профиль, повод, каталог

| Код | Требование | Приоритет |
|---|---|---|
| FR-P01 | Даритель хранит неограниченное число получателей | P0 |
| FR-P02 | Профиль: любимые/нежелательные цвета и цветы, интенсивность запаха (чувствительность), аллергия, астма, домашние животные, стиль, формат композиции | P0 |
| FR-P03 | Каждое поле: `value`, `source`, `confidence`, `updated_at` | P0 |
| FR-P04 | Приватная ссылка одноразовая, с ограниченным сроком, не раскрывает подарок, не индексируется (`noindex`, `X-Robots-Tag`) | P1 |
| FR-P05 | Получатель выбирает, какие ответы можно использовать в будущем (`reusable`) | P1 |
| FR-O01 | Повод: тип, отношения, дата, бюджет (min/max), место, формальность, эмоциональная цель | P0 |
| FR-C01 | Каталог: ботаническое и торговое название, цвет, запах, сезонность, цена, цена со скидкой и срок скидки, уход, ограничения | P0 |
| FR-C02 | Букет: состав, число стеблей, упаковка, цена, доступность, магазин | P0 |
| FR-C03 | Неопознанное растение требует подтверждения флориста (до подтверждения — BLOCK) | P0 |
| FR-C04 | Подарки: категория (открытка, сладости, мягкая игрушка, ароматы, украшения, свеча, другое), состав/аллергены, цена, цена со скидкой, магазин, доступность | P0 |
| FR-C05 | Магазин: название, адрес, координаты, часы работы | P0 |

**Ключи профиля** (`recipient_attributes.key`) и формат `value`:

| key | value | Пример |
|---|---|---|

| Код | Требование |
|---|---|
| FR-R01 | Известные аллергены и риски для животных применяются **до ranking** — к букетам и к подаркам (включая пищевые аллергены) |
| FR-R02 | При неизвестных ограничениях увеличивается доля нейтральных вариантов и снижается confidence |

### 6.3 AI-ассистент по бюджету

| Код | Требование |
|---|---|
| FR-G01 | Даритель вводит бюджет; ассистент формирует **2–3 набора** «букет + доп. подарки», сумма каждого ≤ бюджета |
| FR-G02 | Ассистент работает **только в рамках каталога**: ответ — структурированный JSON с ID позиций; позиции вне каталога не предлагаются |

| FR-G04 | Даритель может исключить позицию из набора; ассистент подбирает замену в рамках оставшегося бюджета с повторной проверкой ограничений |

| Код | Требование |
|---|---|

| Код | Требование |

## 7. Rules Engine — `internal/rules` (ядро безопасности)

Чистый Go-пакет без зависимостей от БД, HTTP и LLM. Вызывается из рекомендаций, ассистента,
фильтров, валидации замен и офлайн-оценки. **Эталонная реализация на Python уже написана и
протестирована (26 тестов) — ниже её точная спецификация; перенеси поведение 1:1.**

### 7.1 Принципы
1. **«Не знаю» ≠ «нет ограничения».** Неизвестное поле никогда не даёт ALLOW по умолчанию для
   рискованной позиции: такая позиция получает WARN, штраф к confidence и попадает в `missing_info`.
2. **«Предполагаю» для ограничений трактуется как «знаю»** (консервативно). Поле считается известным,
   если `confidence != unknown && value != null`.
3. Неопознанное растение, неизвестная токсичность для указанного питомца, неизвестный состав
   подарка при известных аллергиях → **BLOCK**: система не утверждает безопасность при неизвестном составе.
4. **BLOCK окончательный.** Ranker, нумерология, фильтры, ассистент и ручные действия не могут его снять.

### 7.2 Типы

```go
type Confidence string // "know" | "assume" | "unknown"
type Source     string // "giver" | "recipient" | "feedback" | "system"
type Level      string // "none" < "low" < "medium" < "strong"  (Rank(): 0..3)
type Toxicity   string // "none" | "mild" | "moderate" | "severe" | "unknown"
type Decision   string // "allow" | "warn" | "block"

type Attribute struct { Value any; Source Source; Confidence Confidence }
type Profile   map[string]Attribute // отсутствие ключа = unknown

type PlantTaxon struct {
    ScientificName, Genus, Family string
    PetToxicity   map[string]Toxicity // "cat","dog","horse"
    Pollen        Level
    AllergenCodes []string
}
type Flower struct { ID int64; TradeName, Color string; Scent Level; Taxon *PlantTaxon; TaxonConfirmed bool }
type BouquetItem struct { Flower Flower; Stems int }
type Bouquet struct { ID int64; Name string; Items []BouquetItem; Price decimal }
type GiftItem struct {
    ID int64; Name, Category string; Price decimal
    AllergenCodes *[]string // nil = состав неизвестен; &[]string{} = проверено, аллергенов нет
    Scent Level
    PetHazard *bool        // nil = неизвестно
}

type Violation struct {
    Code string; Decision Decision; Message string
    Attribute string; Source Source; Item string
    ConfidencePenalty float64
}
type Result struct {
    Kind string; ItemID int64
    Violations []Violation
    MissingInfo []string // множество
}
// Decision(): BLOCK если есть хоть один BLOCK, иначе WARN если есть WARN, иначе ALLOW
// ConfidenceMultiplier(): max(0.2, 1 - Σ penalty по WARN)
// GiverView(): см. 7.6
```

Деньги — целые тиыны (`int64`) или `shopspring/decimal`, **не float**.

**Коды аллергенов** (lowercase): `genus:<род>`, `family:<семейство>`, `pollen`, `food:<группа>[:<подгруппа>]`
(`food:nuts`, `food:nuts:hazelnut`, `food:peanut`, `food:milk`, `food:gluten`, `food:egg`, `food:soy`,
`food:honey`, `food:cocoa`), `fragrance`, `latex`.
**Матчинг:** аллергия `a` совпадает с кодом позиции `c`, если `c == a` или `c` начинается с `a + ":"`.

**Ключи аллергенов растения:** `genus:<genus>`, `family:<family>`, все `AllergenCodes`, и `pollen`,
если `Pollen ≥ medium`.

### 7.3 Правила для цветка (для каждого цветка в букете)

| # | Условие | Решение | Код | Штраф |
|---|---|---|---|---|
| F1 | `Taxon == nil` или `!TaxonConfirmed` | BLOCK, дальше цветок не проверять | `UNVERIFIED_PLANT` | — |
| F2 | allergies известны и есть пересечение с ключами растения | BLOCK | `ALLERGEN_MATCH` | — |
| F3 | allergies неизвестны и (семейство ∈ {asteraceae, liliaceae, amaryllidaceae, oleaceae} или пыльца ≥ medium) | WARN, missing `allergies` | `ALLERGY_UNKNOWN` | 0.15 |
| F4 | pets известны; для каждого вида: вид ∉ {cat,dog,horse} | WARN | `PET_NO_DATA` | 0.20 |
| F5 | pets известны; токсичность для вида ≠ none (включая unknown) | BLOCK | `PET_TOXIC` | — |
| F6 | pets неизвестны; токсичность для cat или dog ≠ none | WARN, missing `pets` | `PETS_UNKNOWN` | 0.35 если severe/unknown, иначе 0.15 |
| F7 | род ∈ disliked_flowers | WARN (конфликтующий фактор) | `DISLIKED_FLOWER` | 0 |
| F8 | цвет ∈ disliked_colors | WARN | `DISLIKED_COLOR` | 0 |

Пустой букет → BLOCK `EMPTY_COMPOSITION`.

### 7.4 Правила запаха и астмы (букет целиком и подарки-ароматы)

Запах букета = max запаха цветов; пыльца = max пыльцы таксонов.

| # | Условие | Решение | Код | Штраф |
|---|---|---|---|---|
| S1 | asthma = true; запах strong или пыльца strong | BLOCK | `ASTHMA_TRIGGER` | — |
| S2 | asthma = true; запах или пыльца medium | WARN | `ASTHMA_CAUTION` | 0.10 |
| S3 | asthma неизвестна; запах или пыльца strong | WARN, missing `asthma` | `ASTHMA_UNKNOWN` | 0.10 |
| S4 | чувствительность strong; запах ≥ medium | BLOCK | `SCENT_TOO_STRONG` | — |
| S5 | чувствительность medium; запах strong → BLOCK; запах medium → WARN | BLOCK/WARN | `SCENT_TOO_STRONG`/`SCENT_CAUTION` | 0.05 |
| S6 | чувствительность low; запах strong | WARN | `SCENT_CAUTION` | 0.05 |
| S7 | чувствительность неизвестна; запах strong | WARN, missing `scent_sensitivity` | `SCENT_UNKNOWN` | 0.10 |

### 7.5 Правила для подарка

| # | Условие | Решение | Код | Штраф |
|---|---|---|---|---|
| G1 | состав неизвестен (`nil`) и известны непустые аллергии | BLOCK | `UNKNOWN_COMPOSITION` | — |

### 7.6 Наборы, замены, отбор, уточняющий вопрос, приватность

- `CheckGiftSet(bouquet, gifts, budget, profile)` — объединяет результаты букета и всех подарков;
  `total > budget` → BLOCK `OVER_BUDGET`; повтор позиции → BLOCK `DUPLICATE_ITEM`. (FR-G01, AC-4, AC-5)
- `ValidateSubstitution(bouquet, fromFlowerID, toFlower, profile) (Bouquet, Result, error)` —
  строит новый состав (если заменяющий цветок уже есть — стебли суммируются), прогоняет `CheckBouquet`.
  `fromFlowerID` не в букете → ошибка. API при BLOCK отвечает **409** и пишет `audit_events`
  `substitution.blocked`. (FR-S01, AC-3)
- `FilterCandidates(bouquets, profile) (allowed, excluded)` — вызывается **до** ranker. (FR-R01)
- `BestClarifyingQuestion(results)` — для каждого атрибута из `missing_info` суммирует штрафы WARN
  по всем кандидатам; спрашивает про атрибут с максимальной суммой. Нет неизвестных → `nil`. (FR-R04)
  Тексты вопросов:
  - allergies — «Есть ли у получателя аллергия на цветы, пыльцу или продукты?»
  - pets — «Есть ли у получателя дома кошка, собака или другие животные?»
  - asthma — «Есть ли у получателя астма или чувствительность дыхательных путей?»
  - scent_sensitivity — «Как получатель относится к сильным запахам?»
- `GiverView()` — **приватность (раздел 10 ТЗ):** если нарушение вызвано полем с `source = recipient`,
  дарителю показывается только `{"code":"RECIPIENT_RESTRICTION","message":"Не подходит по ограничениям получателя"}`
  — без названия аллергена, растения-причины и т.п. Повторы схлопываются. Остальные нарушения показываются как есть.
  **Все** ответы API для роли giver проходят через GiverView — проверь это тестом на уровне HTTP.

### 7.7 Обязательные тесты `internal/rules` (порт эталонных)
1. AC-1: каталог из роз, лилий+роз, гербер, хризантем, орхидей. Профиль «всё известно, ограничений нет»
   и профиль «владелец кошки» дают разные множества допущенных; у кошатника исключены лилии и хризантемы, розы допущены.
2. AC-2: при пустом профиле букет с лилиями → WARN, `allergies ∈ missing_info`, multiplier меньше,
   чем при «аллергий нет (know)», где решение ALLOW. `allergies = null + unknown` тоже даёт missing.
3. Подарок с неизвестным составом (sweets): пустой профиль → WARN; аллергия на глютен → BLOCK; «аллергий нет» → ALLOW.
4. AC-3: замена роза→лилия у кошатника → BLOCK `PET_TOXIC`; лилия→роза в букете «лилии+розы» → ALLOW и 1 позиция с 10 стеблями;
   замена на неопознанное растение → BLOCK `UNVERIFIED_PLANT`; замена цветка, которого нет в букете → error.
5. AC-4: розы 12 000 + мишка 6 000 + открытка 800 при бюджете 18 000 → BLOCK `OVER_BUDGET`; без открытки — ALLOW.
6. AC-5: аллергия `food:nuts`, конфеты с `food:nuts:hazelnut` → BLOCK, в сообщении `food:nuts:hazelnut`.
7. `assume` + кошка → лилии BLOCK.
8. Питомцы неизвестны: у лилий (severe для кошки) штраф больше, чем у хризантем (mild).
9. Аллергия `family:asteraceae` блокирует герберы; `genus:lilium` — нет.
10. Астма блокирует лилии и парфюм, орхидея (без запаха и пыльцы) — ALLOW.
11. Эвкалипт (medium): чувствительность strong → BLOCK, medium → WARN.
12. Конфеты с `PetHazard=true` + собака → BLOCK.
13. Кролик → WARN `PET_NO_DATA`.
14. Нелюбимая роза → WARN `DISLIKED_FLOWER`, не BLOCK.
15. Пустой букет → BLOCK.
16. GiverView: аллергия на лилию, указанная **получателем** → `suitable=false`, в JSON нет «lilium» и «аллерги»;
    указанная **дарителем** → код `ALLERGEN_MATCH` виден.
17. Уточняющий вопрос: известно всё, кроме питомцев → вопрос про `pets`; полный профиль → `nil`.
18. Property-тест: для каждого вида cat/dog/horse и каждого таксона из справочника — если токсичность ≠ none,
    однокомпонентный букет всегда BLOCK.

## 8. Ranking — `internal/ranking`

### 8.1 Baseline: взвешенный content score
Работает только по `allowed` из Rules Engine. Каждый фактор ∈ [0,1], веса — в конфиге (`ranking.yaml`),
версия весов = `model_version`.

| Фактор | Вес (старт) | Как считать |
|---|---|---|
| `flower_match` | 0.25 | доля стеблей любимых родов; −0.5 за нелюбимые (клип в [0,1]); неизвестно → 0.5 |
| `color_match` | 0.15 | аналогично по цветам |
| `occasion_fit` | 0.20 | таблица соответствия (повод × эмоция × формальность → стиль/цвета/формат), хранится в коде/конфиге |
| `style_format` | 0.10 | совпадение стиля и формата композиции |
| `budget_fit` | 0.15 | 1 внутри [min,max], линейно убывает при цене < min; > max — исключить из Top-5 |
| `season_avail` | 0.10 | в сезоне на дату повода и в наличии |
| `neutrality` | 0.05 | бонус за «нейтральность» (без запаха, низкая пыльца, нетоксично) — **усиливается** пропорционально числу неизвестных полей (FR-R02): `w_neutral = 0.05 + 0.05 × unknown_count` (с перенормировкой весов) |
| `numerology` | 0…0.15 | только если включено; см. 8.3 |

**Confidence** = `base_confidence(профиль) × result.ConfidenceMultiplier()`, где `base_confidence` —
доля известных ключевых полей (allergies, pets, asthma, scent_sensitivity, liked_*, style) с весами.
Калибровать на экспертном наборе (Platt/isotonic), чтобы ECE был ниже, чем у некалиброванной версии.

### 8.2 Карточка Top-5 (FR-R03)
```json
{
  "bouquet_id": 12, "rank": 1, "score": 0.81, "confidence": 0.64,
  "reasons": ["Любимые цвета: белый, розовый", "Подходит к поводу «благодарность»"],
  "conflicts": ["Получатель не любит розы"],
  "missing_info": ["pets"],
  "warnings": [ /* GiverView().reasons */ ],
  "numerology": { "number": 7, "meaning": "...", "label": "развлекательная функция" },
  "shop": { "id": 3, "name": "...", "distance_m": null },
  "price": 15000, "discount_price": 12900, "discount_until": "2026-11-01T00:00:00Z"
}
```
Плюс на уровне ответа: `clarifying_question`, `excluded_count`, `run_id`.
Разнообразие: в Top-5 не больше 2 букетов из одного магазина и не больше 3 с одинаковым доминирующим родом.

### 8.3 Нумерология (FR-N01–N07)
- `NumerologyNumber(date)`: сумма всех цифр `YYYYMMDD`; пока > 9 и ∉ {11,22,33} — снова сумма цифр.
  Тесты: `1990-03-15` → 1+9+9+0+0+3+1+5 = 28 → 10 → 1; подобрать даты, дающие 11, 22 и 33, и проверить, что они не сводятся.
- Фактор = совпадение родов/цветов букета с `numerology_table` активной версии ∈ [0,1].
- Вес ≤ 0.15, остальные веса перенормируются на (1 − w). Не влияет на Rules Engine (тест AC-7:
  включение нумерологии не меняет множества `excluded`).
- В `recommendation_runs`: `numerology_used`, `numerology_version_id`.
- `cmd/eval` всегда считает метрики с выключенным фактором.

### 8.4 Улучшенная модель (P1)
Pairwise learning-to-rank (логистическая регрессия на разностях признаков пар из экспертного
набора, чистый Go, без внешних ML-библиотек) **или** Bayesian ranking. Признаки — те же факторы
из 8.1 без нумерологии. Сравнение с baseline на одном split (RM-05).

## 9. AI-ассистент — `internal/assistant` (FR-G01–G04)

### 9.1 Поток
1. Кандидаты: букеты из `FilterCandidates` (allowed) + подарки, у которых `CheckGift` ≠ BLOCK,
   в наличии, цена ≤ бюджета. Букеты — Top-N (≤ 15) по score, подарки — до 30.
2. LLM получает **только** эти позиции (id, название, категория, цена, краткие признаки, предупреждения),
   повод и бюджет. Персональные данные получателя (аллергии и т.п.) в промпт **не передаются** — они уже применены.
3. Ответ — строго JSON по схеме (используй tool use / structured output):
   ```json
   {"sets":[{"bouquet_id":12,"gift_ids":[101,102],"reasons":["..."],"title":"Нежный"}]}
   ```
4. **Валидация в коде** для каждого набора: все ID существуют в списке кандидатов (иначе набор отбрасывается),
   `CheckGiftSet` ≠ BLOCK, сумма ≤ бюджета. Цена, остаток и предупреждения считаются **кодом**, не берутся у LLM.
5. Если после валидации наборов < 2 — один повторный запрос с перечнем ошибок, затем fallback (9.4) добирает недостающие.
6. Сохранить в `gift_sets`, вернуть: состав, `total_price`, `budget_left`, `reasons`, `warnings` (GiverView). (FR-G03)

### 9.2 Исключение позиции (FR-G04)
`POST /gift-sets/{id}/exclude {item_type, item_id}` → новый набор (`parent_set_id`), исключённая позиция
не предлагается снова для этого набора, замена подбирается в пределах `budget − (сумма оставшихся)`,
повторная проверка `CheckGiftSet`. Если замены нет — вернуть набор без неё и сообщение.

### 9.3 Разнообразие
2–3 набора должны отличаться букетом или минимум двумя подарками; разные «характеры» (например, «классика»,
«ярко», «практично»).

### 9.4 Детерминированный fallback (без LLM)
Жадный подбор: для 3 лучших по score букетов, укладывающихся в бюджет, добавлять подарки по убыванию
`relevance/price` из разных категорий, пока помещаются; открытка — приоритет, если осталось ≥ её цены.
Используется без `ANTHROPIC_API_KEY` и в тестах. Ответ помечается `generator: "fallback" | "llm"`.

## 10. Фильтры — `internal/offers` (FR-L01–L05)

`GET /api/v1/offers?filter=nearby,discount&lat=..&lon=..&run_id=..` — фильтры комбинируются через запятую.

- **Базовое множество** — всегда результат Rules Engine для текущего получателя (`run_id` → occasion → profile). (FR-L05)
- **nearby**: расстояние по формуле гаверсинуса, сортировка по возрастанию; `lat/lon` берутся только из запроса,
  **не сохраняются** нигде (middleware логирования должен вырезать их из query; тест на это). Ответ содержит
  `distance_m`, `open_now`, часы работы (с учётом `timezone` магазина).
- **cheaper**: параметр `bouquet_id`; среди допущенных с ценой < текущей выбрать вариант с минимальным `|score − score_current|`;
  вернуть `price_diff`. Если нет — пустой ответ с сообщением.
- **discount**: только позиции, где `now ∈ [discount_from, discount_until)`; показать `price`, `discount_price`, `discount_until`.
- Эффективная цена = цена со скидкой, если скидка действует.

Frontend: запрос разрешения геолокации только по клику «Рядом»; при отказе — ручной выбор точки на карте.

## 11. ML и оценка — `internal/eval`, `cmd/eval`

| Метрика | Требование |
|---|---|
| NDCG@5 | выше baseline, 95% CI (bootstrap по получателям, 1000 итераций, фиксированный seed) |
| Unsafe recommendation rate (букеты и подарки) | **0** на размеченном test |
| Нарушение бюджета в наборах | **0** |
| Coverage | ≥ 30% каталога попадает хотя бы в один Top-5 на test |
| ECE | ниже baseline (10 бинов) |
| Robustness | измерить падение NDCG@5 при случайном удалении 30% полей профиля (поле → `unknown`), 5 повторов |

- **Split по получателям** (group split): `case_id` → получатель; один получатель не может быть и в train, и в test. Тест на это.
- Unsafe: экспертные случаи с `is_unsafe=true` + автоматическая проверка «Rules Engine на эталонном профиле» для всех выданных позиций.
- Каждый запуск пишет `research.experiment_runs` (RM-04) и `docs/eval_report.md`.
- `make eval` воспроизводим (seed из флага).

## 13. Безопасность и приватность (раздел 10 ТЗ)

- Ответы получателя недоступны дарителю на уровне конкретного ограничения — даритель видит только
  «подходит / не подходит» (GiverView, §7.6). В `GET /recipients/{id}` поля с `source=recipient`
  возвращаются как `{"key":"allergies","hidden":true}` без значения.
- Значение «не знаю» не преобразуется в отсутствие аллергии (нигде: БД, DTO, фронт — в форме «не знаю» отдельная опция, а не пустое поле).
- Система не утверждает медицинскую безопасность при неизвестном составе. Формулировки UI: «известных
  противопоказаний не найдено», а не «безопасно». Дисклеймер на карточке.
- Геолокация не сохраняется.
- Авторизация: JWT, роли giver/florist/manager; даритель видит только своих получателей (тест на чужой ID → 404).
  Флорист меняет только свой магазин.
- Приглашения (P1): в БД только SHA-256 токена; одноразовость; срок; страница `/public/invite/:token`
  не показывает, что дарят, `noindex`.
- Audit log (`audit_events`): импорт каталога, изменение цен/наличия, замены (approved/blocked),
  изменения нумерологии, согласия, экспорты, удаление профиля.
- Удаление получателя каскадно удаляет атрибуты, включая дату рождения (FR-N07).

## 15. Экраны (раздел 11 ТЗ) — React

**Даритель**
- Получатели: список + создание.
- Профиль: для каждого поля переключатель **«знаю / предполагаю / не знаю»**; при «не знаю» значение не вводится.
  Скрытые поля получателя — плашка «заполнено получателем, скрыто».
- Повод и бюджет: тип, отношения, дата, min/max, место, формальность, эмоция, переключатель **нумерологии** (по умолчанию выкл.).
- Top-5: карточки (§8.2) — score/confidence как шкала, причины, конфликты, «не хватает сведений»,
  предупреждения; **уточняющий вопрос** сверху с быстрыми ответами (ответ сразу обновляет профиль и пересчитывает).
- Наборы «букет + подарки»: 2–3 карточки, итог, остаток бюджета, кнопка «убрать» у каждой позиции.
- Фильтры-чипы «Рядом», «Дешевле», «Со скидкой» (комбинируются) + **карта** магазинов (Leaflet/OSM),
  расстояние, часы, «открыто сейчас».
- Карточка состава букета: цветы, стебли, фото с лицензией, бейджи токсичности/запаха (без раскрытия скрытых ограничений).
- Нумерология на карточке: число, значение, бейдж «развлекательная функция».
- История рекомендаций и feedback.
- Настройки: исследовательский режим (согласие с текстом и версией, отзыв одной кнопкой).

**Флорист / магазин**: каталог (таблица + импорт CSV с отчётом об ошибках), цены и скидки, наличие,
неподтверждённые растения (подтвердить → выбрать таксон), замены (выбор цветка → мгновенная валидация;
опасная — кнопка неактивна и причина; **API всё равно проверяет**).

**Менеджер**: ограничения/правила (просмотр версии Rules Engine и справочника), таблица нумерологии
(редактор + история версий), качество данных (растения без ASPCA, подарки без состава, букеты без фото),
аналитика (запуски, feedback), экспертная разметка (форма оценки 0–3 + причина), evaluation dashboard
(baseline vs модель, NDCG@5 с CI, unsafe, coverage, ECE, robustness).

**Публичная** (P1): анкета получателя по ссылке.

Требования к UI: адаптивность (мобильный даритель), русский язык интерфейса, понятные пустые и
ошибочные состояния, никаких формулировок «гарантированно безопасно».

## 16. Критерии приёмки (раздел 13 ТЗ) → тесты

Каждый критерий — минимум один автоматический тест (Go unit/integration и/или Playwright). Назови тесты `TestAC1_…`.

| AC | Критерий | Где проверять |
|---|---|---|
| AC-1 | При одном бюджете два получателя получают разные рекомендации | rules unit + HTTP integration |
| AC-2 | «Не знаю» не считается отсутствием аллергии | rules unit + DTO/HTTP |
| AC-3 | Опасная замена блокируется в UI и API | API 409 + Playwright (кнопка неактивна) |

## 18. Инженерные практики

Проект живёт долго и работает с чувствительными данными, поэтому это часть задания, а не украшение.

### 18.1 CI (GitHub Actions, с вехи M0)
Один workflow на push и PR: `golangci-lint` → `go test ./... -race -cover` → `go build` →
`govulncheck` → `npm run lint` → `vitest run` → `npm run build` → миграции `up` → `down` → `up`
на чистой базе → Playwright на поднятом compose. Красный CI блокирует merge.

### 18.2 Код и стиль
- Go: `gofumpt`, `golangci-lint` (errcheck, govet, staticcheck, revive, gosec, errorlint, sqlclosecheck).
  Ошибки оборачиваются `fmt.Errorf("…: %w", err)`, в HTTP-слое маппятся в коды §14. `panic` — только при старте.
- Контекст: `context.Context` первым аргументом во всё, что ходит в БД и сеть; таймауты на каждый внешний вызов
  (LLM — 20 с + повтор с backoff, геокодер/плитки карты — не вызываются с бэкенда).
- TypeScript: `strict: true`, ESLint + Prettier, типы API только сгенерированные из `openapi.yaml` — руками не дублировать.
- Транзакции: рекомендация, набор, импорт каталога и отзыв согласия выполняются в одной транзакции.

### 18.3 Миграции и данные
- Только `goose`, только вперёд; у каждой миграции рабочий `Down`, проверяется в CI.
- Схема меняется миграцией, а не правкой Прил. A; Прил. A — снимок первой версии.
- Денежные поля — `numeric(12,2)` в БД и целые тиыны либо `decimal` в коде, никогда `float`.
- Сид-данные (`make seed`) идемпотентны и не затирают ручные правки каталога.

### 18.4 Наблюдаемость
- `log/slog` в JSON, `request_id` в каждой записи, уровень из env.
- **В логи, метрики и трейсы не попадают:** аллергии, астма, питомцы, дата рождения, геолокация,
  токены приглашений, текст промптов с данными получателя. Middleware вырезает `lat`/`lon` из query —
  на это есть тест (FR-L01).
- `/metrics` (Prometheus): латентность и коды ответов по эндпоинтам, число BLOCK по кодам нарушений,
  доля наборов от LLM против fallback, ошибки LLM. Счётчик `rules_block_total{code=...}` — главный
  индикатор здоровья: его резкое изменение означает, что сломались данные или правила.
- `/healthz` (живость) и `/readyz` (БД доступна, миграции применены).

### 18.5 Безопасность эксплуатации
- Секреты только в env, `.env` в `.gitignore`, в репозитории — `.env.example`. Ключ LLM не уходит на фронт.
- Rate limiting: `/auth/*` (по IP), `/recommendations` и `/gift-sets` (по пользователю, из-за стоимости LLM),
  `/public/invites/*` (по токену). CORS — только известные origin.
- Зависимости обновляются Dependabot/Renovate; `govulncheck` в CI.
- Удаление аккаунта удаляет получателей, атрибуты и research-связку (RM-02, FR-N07) — тест на каскад.

### 18.6 Деплой и бэкапы
- Деплой: один хост, `docker compose` + reverse proxy с TLS (Caddy), либо fly.io. Миграции — отдельным шагом
  перед запуском новой версии, а не в `main()`.
- `pg_dump` по расписанию, хранение вне хоста, **проверенное восстановление** с записью в `docs/runbook.md`.
- Версии по semver, git-теги, `CHANGELOG.md` (Keep a Changelog).

## Приложение A. Схема БД (PostgreSQL 16) — `migrations/00001_init.sql`

Проверена на PostgreSQL 16: применяется без ошибок, 25 таблиц, проверено, что срабатывают
CHECK на «know без значения», CHECK бюджета набора, триггер согласия и `research.revoke_consent`.
Для goose оберни в `-- +goose Up` / `-- +goose StatementBegin … StatementEnd` для функций; убери `BEGIN/COMMIT`.

```sql
-- Flowers — схема БД (PostgreSQL 14+)
-- Покрывает таблицы из разделов 9 и 12 ТЗ.
-- Соглашения: id — bigint identity, время — timestamptz, деньги — numeric(12,2) в тенге (KZT).

BEGIN;

-- ─────────────────────────── Справочные типы ───────────────────────────

CREATE TYPE user_role        AS ENUM ('giver', 'florist', 'manager');
CREATE TYPE attr_source      AS ENUM ('giver', 'recipient', 'feedback', 'system');
-- «знаю» / «предполагаю» / «не знаю» (FR-P03). 'unknown' НИКОГДА не означает «нет ограничения».
CREATE TYPE attr_confidence  AS ENUM ('know', 'assume', 'unknown');
CREATE TYPE scent_level      AS ENUM ('none', 'low', 'medium', 'strong');
CREATE TYPE toxicity_level   AS ENUM ('none', 'mild', 'moderate', 'severe', 'unknown');
CREATE TYPE gift_category    AS ENUM ('card', 'sweets', 'soft_toy', 'fragrance', 'jewelry', 'candle', 'other');
CREATE TYPE substitution_status AS ENUM ('proposed', 'approved', 'blocked');

-- ─────────────────────────── Пользователи и магазины ───────────────────────────

CREATE TABLE users (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email         text NOT NULL UNIQUE,
    display_name  text,
    role          user_role NOT NULL DEFAULT 'giver',
    shop_id       bigint,                         -- для флористов (FK ниже)
    created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE shops (                              -- FR-C05
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name          text NOT NULL,
    address       text NOT NULL,
    lat           double precision NOT NULL CHECK (lat BETWEEN -90 AND 90),
    lon           double precision NOT NULL CHECK (lon BETWEEN -180 AND 180),
    -- {"mon":[["09:00","21:00"]], "sun":[]} — несколько интервалов в день
    opening_hours jsonb NOT NULL DEFAULT '{}'::jsonb,
    timezone      text NOT NULL DEFAULT 'Asia/Almaty',
    created_at    timestamptz NOT NULL DEFAULT now()
);
ALTER TABLE users ADD CONSTRAINT users_shop_fk FOREIGN KEY (shop_id) REFERENCES shops(id) ON DELETE SET NULL;

-- ─────────────────────────── Получатели ───────────────────────────

CREATE TABLE recipients (                         -- FR-P01
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    giver_id      bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    nickname      text NOT NULL,                  -- «Мама», «Айгерим»
    created_at    timestamptz NOT NULL DEFAULT now(),
    updated_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX ON recipients (giver_id);

-- EAV: одно поле профиля = одна строка с value/source/confidence (FR-P02, FR-P03).
-- Ключи: allergies, asthma, pets, scent_sensitivity, liked_flowers, disliked_flowers,
--        liked_colors, disliked_colors, style, composition_format, birth_date (FR-N07)
CREATE TABLE recipient_attributes (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    recipient_id  bigint NOT NULL REFERENCES recipients(id) ON DELETE CASCADE,
    key           text NOT NULL,
    value         jsonb,                          -- NULL допустим только при confidence='unknown'
    source        attr_source NOT NULL,
    confidence    attr_confidence NOT NULL,
    -- FR-P05: получатель разрешил использовать ответ в будущем
    reusable      boolean NOT NULL DEFAULT true,
    -- раздел 10: ответ получателя скрыт от дарителя на уровне конкретного ограничения
    hidden_from_giver boolean GENERATED ALWAYS AS (source = 'recipient') STORED,
    updated_at    timestamptz NOT NULL DEFAULT now(),
    UNIQUE (recipient_id, key),
    CHECK (value IS NOT NULL OR confidence = 'unknown')
);

CREATE TABLE recipient_invites (                  -- FR-P04 (P1)
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    recipient_id  bigint NOT NULL REFERENCES recipients(id) ON DELETE CASCADE,
    token_hash    text NOT NULL UNIQUE,           -- храним только хэш токена
    expires_at    timestamptz NOT NULL,
    used_at       timestamptz,                    -- одноразовость
    created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE occasions (                          -- FR-O01
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    recipient_id  bigint NOT NULL REFERENCES recipients(id) ON DELETE CASCADE,
    type          text NOT NULL,                  -- birthday, apology, march8, wedding...
    relationship  text,                           -- partner, mother, colleague...
    date          date,
    budget_min    numeric(12,2) NOT NULL DEFAULT 0 CHECK (budget_min >= 0),
    budget_max    numeric(12,2) NOT NULL CHECK (budget_max > 0),
    place         text,                           -- home, office, restaurant...
    formality     smallint CHECK (formality BETWEEN 1 AND 5),
    emotion_goal  text,                           -- joy, gratitude, romance, support...
    numerology_enabled boolean NOT NULL DEFAULT false,  -- FR-N01
    created_at    timestamptz NOT NULL DEFAULT now(),
    CHECK (budget_min <= budget_max)
);

-- ─────────────────────────── Ботаника и каталог ───────────────────────────

CREATE TABLE plant_taxa (                         -- GBIF + ASPCA
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    gbif_key      bigint UNIQUE,
    scientific_name text NOT NULL UNIQUE,         -- 'Lilium'
    genus         text NOT NULL,
    family        text NOT NULL,                  -- 'Liliaceae'
    -- ASPCA: {"cat":"severe","dog":"none","horse":"none"}
    pet_toxicity  jsonb NOT NULL DEFAULT '{"cat":"unknown","dog":"unknown","horse":"unknown"}'::jsonb,
    aspca_url     text,
    pollen_level  scent_level NOT NULL DEFAULT 'medium',
    allergen_codes text[] NOT NULL DEFAULT '{}',  -- доп. коды, напр. 'latex'
    image_url     text,
    image_license text,                           -- раздел 8: лицензия на каждое изображение
    image_author  text
);

CREATE TABLE flowers (                            -- FR-C01: торговая позиция «цветок»

-- Доступность и цены отделены от карточки: флорист меняет их часто (PUT /availability/{id})
CREATE TABLE availability (
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    bouquet_id    bigint REFERENCES bouquets(id) ON DELETE CASCADE,
    gift_item_id  bigint REFERENCES gift_items(id) ON DELETE CASCADE,
    in_stock      boolean NOT NULL DEFAULT true,
    quantity      integer CHECK (quantity >= 0),
    updated_at    timestamptz NOT NULL DEFAULT now(),
    CHECK ((bouquet_id IS NULL) <> (gift_item_id IS NULL)),
    UNIQUE (bouquet_id),
    UNIQUE (gift_item_id)
);

CREATE TABLE price_offers (                       -- цена, скидка и срок скидки (FR-C01, FR-L04)
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    bouquet_id    bigint REFERENCES bouquets(id) ON DELETE CASCADE,
    gift_item_id  bigint REFERENCES gift_items(id) ON DELETE CASCADE,
    price         numeric(12,2) NOT NULL CHECK (price > 0),
    discount_price numeric(12,2) CHECK (discount_price > 0),
    discount_from timestamptz,
    discount_until timestamptz,
    currency      char(3) NOT NULL DEFAULT 'KZT',
    created_at    timestamptz NOT NULL DEFAULT now(),
    CHECK ((bouquet_id IS NULL) <> (gift_item_id IS NULL)),
    CHECK (discount_price IS NULL OR discount_price < price),
    CHECK (discount_price IS NULL OR discount_until IS NOT NULL)
);
CREATE INDEX ON price_offers (bouquet_id);
CREATE INDEX ON price_offers (gift_item_id);

-- Действующая цена: удобна для фильтров «Дешевле» и «Со скидкой»
CREATE VIEW current_prices AS
SELECT DISTINCT ON (coalesce(bouquet_id, -gift_item_id))
       id AS offer_id, bouquet_id, gift_item_id, price,
       CASE WHEN discount_price IS NOT NULL
             AND now() >= coalesce(discount_from, '-infinity') AND now() < discount_until
            THEN discount_price END AS active_discount_price,
       discount_until
FROM price_offers
ORDER BY coalesce(bouquet_id, -gift_item_id), created_at DESC;

CREATE TABLE research.research_consents (         -- RM-01, RM-02
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id       bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    consent_version text NOT NULL,

    revoked_at    timestamptz
);

CREATE TABLE research.research_subjects (
    research_id   uuid PRIMARY KEY,
    user_id       bigint NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
    created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE research.experiment_runs (           -- RM-04, RM-05
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    model_version text NOT NULL,
    dataset_version text NOT NULL,
    split_id      text NOT NULL,                  -- baseline и модель сравниваются на одном split
    seed          integer NOT NULL,
    params        jsonb NOT NULL DEFAULT '{}'::jsonb,
    -- {"ndcg@5":{"mean":0.71,"ci95":[0.66,0.75]}, "unsafe_rate":0, "coverage":0.42, "ece":0.08}
    metrics       jsonb NOT NULL,
    numerology_in_features boolean NOT NULL DEFAULT false,  -- RM-07, FR-N06

CREATE TABLE research.research_exports (          -- RM-06
    id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    requested_by  bigint REFERENCES users(id),
    dataset_version text NOT NULL,
    data_dictionary_version text NOT NULL,
    min_group_size integer NOT NULL DEFAULT 5 CHECK (min_group_size >= 5),
    row_count     integer,
    file_uri      text,
    created_at    timestamptz NOT NULL DEFAULT now()
);

-- Критерий приёмки 10: без согласия в research-таблицах нет записей.
CREATE FUNCTION research.require_consent() RETURNS trigger AS $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM research.research_consents c
                   WHERE c.user_id = NEW.user_id AND c.revoked_at IS NULL) THEN
        RAISE EXCEPTION 'research: no active consent for user %', NEW.user_id;
    END IF;
    RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER research_subjects_need_consent
    BEFORE INSERT ON research.research_subjects
    FOR EACH ROW EXECUTE FUNCTION research.require_consent();

-- RM-02: отзыв согласия в один шаг — удаляет связку, данные выпадают из будущих экспортов.
CREATE FUNCTION research.revoke_consent(p_user_id bigint) RETURNS void AS $$
BEGIN
    UPDATE research.research_consents SET revoked_at = now()
     WHERE user_id = p_user_id AND revoked_at IS NULL;
    DELETE FROM research.research_subjects WHERE user_id = p_user_id;
END $$ LANGUAGE plpgsql;

COMMIT;
```
