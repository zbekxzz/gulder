# 0005. Rules Engine: порт по спецификации и принятые трактовки

- Статус: принято (M2)

## Контекст
§7 просит перенести 1:1 эталонную Python-реализацию (26 тестов), но её нет в репозитории —
есть только спецификация §7.2–7.7. Некоторые места спецификации допускают несколько прочтений.

## Решение
`internal/rules` реализован по таблицам §7.3–7.6, все 18 обязательных тестов §7.7 портированы
(имена с кодами AC), покрытие пакета 100%. Трактовки:

1. **Пустой/неизвестный уровень** (`Level("")` или мусор) имеет ранг `strong`: ошибка в данных должна
   включать правила, а не выключать их. Каталог из БД всегда задаёт уровень явно.
2. **F4 (питомец вне cat/dog/horse)** — WARN `PET_NO_DATA`, а не BLOCK (так требует тест №13),
   хотя принцип 3 говорит о BLOCK для «неизвестной токсичности для указанного питомца». BLOCK действует
   для cat/dog/horse, если токсичность в справочнике `unknown` или не задана.
3. **F6**: штраф 0.35, если токсичность для кошки *или* собаки `severe`/`unknown`, иначе 0.15.
4. **Значение неверного типа** (например, `asthma: "yes"`) считается неизвестным — правило работает
   консервативно (WARN), а API не даёт записать такое значение.
5. **Дубликаты** `(code, item, attribute)` схлопываются с сохранением первого нарушения.
6. **Уточняющий вопрос**: при равной пользе порядок — allergies, pets, asthma, scent_sensitivity.
7. **GiverView** скрывает *любое* нарушение, вызванное полем с `source=recipient`, включая WARN
   (например, «не любит розы»), одной причиной `RECIPIENT_RESTRICTION`.
8. **Совпадение аллергенов** — по сегментам кода: `food:nut` не совпадает с `food:nuts`.
9. **Замена на тот же цветок, что уже есть в букете**, суммирует стебли; иначе новый цветок встаёт на место заменяемого.

## Альтернативы
Ждать эталонную реализацию — блокирует всё остальное (M3+ опираются на правила).

## Следствия
Если эталонная реализация найдётся, её 26 тестов нужно прогнать против этого пакета и разобрать
расхождения отдельными ADR. Версия правил — `rules.Version`, пишется в каждый запуск рекомендаций.
